GAP A — APOD Image URL

FINDING

A1 — Does NASAClient already fetch image_url / hd_image_url / media_type?

Yes — completely. The image fields are fetched, normalised, and stored in the Pydantic model at every request. Proof from nasa_client.py line 199–201 and line 208–216:

url = raw.get("url")              # → image_url
hdurl = raw.get("hdurl")          # → hd_image_url
copyright_ = raw.get("copyright") # → copyright
media_type = raw.get("media_type", "image")  # already captured line 190

return NASAAPODData(
    title=title,
    explanation=explanation,
    date=date_str,
    media_type=media_type,          # ✅ present in model
    image_url=url,                  # ✅ present in model
    hd_image_url=hdurl,             # ✅ present in model
    copyright=copyright_,           # ✅ present in model
    additional_data=additional,
)

The NASAAPODData model in models.py has four fully typed optional fields:

media_type: str                    # always present (defaults to "image")
image_url: Optional[str] = None   # NASA APOD "url" field
hd_image_url: Optional[str] = None# NASA APOD "hdurl" field
copyright: Optional[str] = None   # NASA APOD "copyright" field

A2 — Where is this data currently lost?

The data is fetched, validated, and held in memory perfectly. It is then deliberately discarded at exactly one point — the static method StoryGenerator._ensure_source_data() in story_generator.py lines 181–198. This method only writes three fields into source_data:

existing.update({
    "source": apod.source,   # ✅ written
    "date": apod.date,       # ✅ written
    "title": apod.title,     # ✅ written
                             # ❌ image_url     NOT written
                             # ❌ hd_image_url  NOT written
                             # ❌ media_type    NOT written
                             # ❌ copyright     NOT written
})

Because source_data is typed as dict[str, Any] in SpaceStory, extra keys are accepted without any schema change. The data loss is purely in this one method.

Exact data flow showing where fields are dropped:
NASA raw JSON → NASAAPODData (all 4 fields present) → _ensure_source_data() ← DATA LOST HERE → SpaceStory.source_data (only 3 fields)

A3 — What is the smallest backend change required?

A 4-line addition to _ensure_source_data() in story_generator.py. No new models, no new endpoints, no new routes, no schema changes. The existing source_data: dict[str, Any] field on SpaceStory already accepts arbitrary keys:

existing.update({
    "source": apod.source,
    "date": apod.date,
    "title": apod.title,
    "media_type": apod.media_type,
    "image_url": apod.image_url,       # None when not present — safe to omit in UI
    "hd_image_url": apod.hd_image_url, # None when not present
    "copyright": apod.copyright,       # None when not present
})

Safety properties of this change

  • image_url and hd_image_url are already Optional[str] — they can be null in the JSON (e.g., when media_type == "video"). The frontend must always null-check before rendering an <img> tag.
  • media_type is always a string — it will be "image" or "video". The frontend uses this to decide whether to render an image or a video notice.
  • copyright is Optional[str] — used for proper attribution text. Not a secret. The NASA APOD page itself displays it publicly.
  • No API keys, no prompt content, no model names are exposed.
  • The existing _ensure_source_data unit tests in tests/test_models.py (lines 236–294) will still pass — they verify the three authoritative fields, and test case 5 explicitly confirms extra keys are preserved, not clobbered.
  • This change only affects the generate_daily_story() and generate_apod_story_with_context() pipelines. The generate_from_context() path has no APOD object, so it correctly won't call _ensure_source_data with image fields — that path remains unchanged.
Verdict — Gap A: One method, four new lines. No model changes, no new endpoints, no schema migrations, no test breakage. This is a MINIMAL surgical change.

FINDING

The backend already fetches DONKI CME (Coronal Mass Ejection) events every time /api/daily-news is called. This is done in StoryGenerator._fetch_donki_optional() → NASAClient.get_donki_cme().

B2 — What does a real NASA DONKI CME response contain?

Based on the official NASA DONKI API (publicly documented at https://api.nasa.gov/DONKI/CME), each CME event item contains:

{
  "activityID": "2024-06-14T10:00:00-CME-001",
  "catalog": "M2M_CATALOG",
  "startTime": "2024-06-14T10:00Z",         // → begin_time (already extracted)
  "sourceLocation": "S15E25",               // sunspot location — useful
  "activeRegionNum": 13699,                 // active region number — useful
  "link": "https://kauai.ccmc.gsfc.nasa.gov/...",
  "note": "CME with Type II radio burst",   // narrative context — useful
  "instruments": [{"displayName": "LASCO C2"}, ...],
  "cmeAnalyses": [
    {
      "time21_5": "2024-06-14T18:00Z",
      "latitude": -15,
      "longitude": 20,
      "halfAngle": 30,
      "speed": 850,                         // km/s — highly useful for display
      "type": "S",                          // speed type (S/C/O)
      "isMostAccurate": true,
      "enlilList": [
        {
          "estimatedShockArrivalTime": "2024-06-17T03:00Z",  // Earth arrival — key info
          "estimatedDuration": "18",
          "rmin_re": null,
          "kp_18": null,
          "kp_90": 5,                       // estimated Kp index — geomagnetic impact
          "kp_135": null,
          "kp_180": null,
          "isEarthGB": true,                // Earth-directed flag
          "link": "...",
          "impactList": [...]
        }
      ]
    }
  ],
  "linkedEvents": [
    {"activityID": "2024-06-14T10:30:00-FLR-001"}  // linked flare — already extracted
  ]
}

B3 — Is DONKI data currently exposed through any API endpoint?

No. This is the core gap. The DONKI events are fetched, normalised, passed into the AI prompt as context, and then completely discarded. They never appear in the final JSON response. The AI uses them when generating the story text, but the raw structured CME data is not returned to the frontend.

NASA DONKI CME API → NASAClient.get_donki_cme() [fetched] → _filter_donki_events() [filtered] → build_apod_with_donki_prompt() [injected into AI prompt text only] → AI generates story text ← CME data used here (as prompt context) → SpaceStory returned ← NO CME fields in response → /api/daily-news JSON ← DONKI data ABSENT from response

B4 — Is existing DONKI data sufficient for a useful solar-storm section?

Yes — with minimal normalisation of already-fetched data. The NASADONKIEvent.raw field stores the complete CME payload. The fields most relevant to a space-weather dashboard section are already present in the raw data and can be surfaced without any new NASA API calls:

Dashboard needField in raw CME payloadAvailable?
Event timestampstartTimeYes (already in begin_time)
CME speed (km/s)cmeAnalyses[0].speedYes (in raw)
Earth-directed flagcmeAnalyses[0].enlilList[0].isEarthGBYes (in raw)
Estimated Earth arrivalcmeAnalyses[0].enlilList[0].estimatedShockArrivalTimeYes (in raw)
Geomagnetic impact (Kp index)cmeAnalyses[0].enlilList[0].kp_90Yes (in raw)
Source region locationsourceLocationYes (in raw)

Caution: The fields inside cmeAnalyses and enlilList are deeply nested and optional. Real NASA DONKI responses frequently have null or missing analyses (especially for slower CMEs). The backend must handle graceful nulls — and the frontend must never display a speed or arrival time it did not receive.

B5 — What additional NASA endpoint, if any, is needed?

No additional NASA API endpoint is needed for an MVP space-weather section. Everything described above comes from the /DONKI/CME endpoint already called by NASAClient.get_donki_cme().

However, three additional DONKI event types are available on the same base URL (https://api.nasa.gov/DONKI/) that could enrich the dashboard in a future iteration — but are not required now:

B6 — Proposed API response shape for space-weather data

The backend should add a new field space_weather to the existing /api/daily-news response. This field is populated from the DONKI CME events already fetched in the same pipeline call. No new endpoint needed.

{
  "success": true,
  "data": {
    // ... existing SpaceStory fields unchanged ...
    "title": "...",
    "summary": "...",
    "source_data": { ... },

    "space_weather": {                         // NEW FIELD — added by backend
      "available": true,                       // false when DONKI returned 0 events
      "event_count": 2,                        // number of CME events in response
      "events": [
        {
          "event_type": "CME",
          "begin_time": "2024-06-14T10:00Z",   // from NASADONKIEvent.begin_time
          "speed_kmps": 850,                   // from raw.cmeAnalyses[0].speed (null if absent)
          "is_earth_directed": true,           // from raw...enlilList[0].isEarthGB (null if absent)
          "estimated_arrival": "2024-06-17T03:00Z", // from enlilList[0].estimatedShockArrivalTime
          "kp_index": 5,                       // from enlilList[0].kp_90 (null if absent)
          "source_location": "S15E25",         // from raw.sourceLocation (null if absent)
          "note": "CME with Type II radio burst" // from raw.note (null if absent)
        }
      ]
    }
  }
}
Design rule: Every field inside each event object must be explicitly nullable. The frontend renders a field only when its value is a non-null, non-empty string or number. If space_weather.available == false or events == [], the space-weather section shows a deliberate "no active events" state — never fabricated data.
