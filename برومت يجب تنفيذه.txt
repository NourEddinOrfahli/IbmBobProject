# TASK: Add an AI Explanation Action to Every Space Weather Event

## Objective

Improve the Space Weather section of the Space Interpreter application by adding an interactive AI explanation action to every individual space-weather event card.

The user should be able to click a button such as:

"Explain with AI"

and be taken directly to the existing Space AI Chat interface with the selected event already loaded as context.

The goal is to make complex NASA/DONKI space-weather data understandable to non-experts while keeping the existing dashboard behavior unchanged.

This feature must feel like a natural part of the product, not a separate utility.

---

# 1. FIRST: Inspect the Existing Codebase

Before modifying anything:

1. Inspect the current frontend structure.
2. Find the component responsible for rendering individual space-weather/CME event cards.
3. Find the existing Space Chat component/page and its routing.
4. Find the current chat API implementation.
5. Find the current TypeScript types for:
   - Space weather
   - CME events
   - Chat requests/responses
6. Find how navigation is currently implemented.
7. Find the existing Arabic RTL design system and reusable button components.

Do NOT create duplicate components or duplicate chat functionality if an existing implementation already exists.

Do NOT modify unrelated features.

---

# 2. Add "Explain with AI" to Every Event Card

Every individual space-weather event card must contain a clearly visible action button.

Recommended Arabic label:

"اشرح هذا الحدث بالذكاء الاصطناعي"

Optional smaller English label:

"Explain with AI"

The button should be visually consistent with the existing Space Interpreter design.

It should:

- Be clearly clickable.
- Have an AI/chat icon if an existing icon library is already used.
- Work with keyboard navigation.
- Have an accessible aria-label.
- Have a visible hover/focus state.
- Not interfere with the rest of the card.
- Not trigger when the user clicks elsewhere on the card.
- Work correctly on desktop and mobile.

Do not add a heavy animation library.

Use the existing styling system.

---

# 3. Pass the Selected Event to the AI Chat

When the user clicks the button, the application must preserve the complete context of the selected event.

The Chat page/component should receive structured context containing, when available:

- Event type
- Begin time
- Speed in km/s
- Whether the event is Earth-directed
- Estimated arrival
- Kp index
- Source location
- NASA/DONKI note
- Any other relevant fields already available in the event object

Do NOT manually reconstruct or invent scientific data.

Use the actual event object returned by the backend.

---

# 4. Preferred Navigation Design

If the application already has a dedicated Chat route, navigate to it.

Preferred behavior:

    Space Weather
          ↓
    User clicks "Explain with AI"
          ↓
    /chat?event=...
          ↓
    Chat opens with selected event context
          ↓
    AI automatically explains the event

However, DO NOT put a large unencoded JSON object directly into the URL.

Use a safe approach appropriate to the existing architecture.

Preferred options, in order:

1. Existing client-side state/context mechanism.
2. Existing chat session/context mechanism.
3. A compact URL parameter containing an encoded event ID/index if the event can be safely reconstructed.
4. If necessary, a serialized URL-safe context with reasonable size limits.

Never expose API keys or secrets.

---

# 5. Automatically Prepare the First User Question

When the user arrives in Chat from an event card, automatically prepare a useful Arabic question.

Example:

"اشرح لي هذا الحدث الفضائي بطريقة مبسطة. ما الذي حدث، وما مدى أهميته، وهل يمكن أن يؤثر على الأرض؟"

The selected event should be included as structured context.

The AI should NOT be forced to invent information.

The explanation should distinguish between:

- Facts directly present in the NASA/DONKI event data.
- Scientific interpretation.
- Uncertainty or missing information.

---

# 6. Important: Do Not Hallucinate Scientific Data

The AI prompt/context for this feature must explicitly instruct the model:

- Use the supplied event data as the primary factual source.
- Do not invent missing measurements.
- Do not invent an estimated arrival time when none exists.
- Do not claim that an event is Earth-directed when the source says it is not.
- Clearly state when information is unavailable.
- Explain scientific terminology in accessible Arabic.
- Avoid unnecessarily technical language.
- Preserve numerical values and units accurately.
- Do not exaggerate the danger or significance of an event.

For example:

If:

is_earth_directed = false

the AI must not describe the event as an Earth-directed CME.

If:

estimated_arrival = null

the AI must say that no estimated arrival time is available.

---

# 7. Chat UX

When the user enters Chat from an event card:

Show a small context panel above or beside the conversation:

"Space Weather Event"

Then display a concise summary such as:

Event Type: CME
Speed: 482 km/s
Source Location: S10W00
Earth Directed: No

Use the actual values from the selected event.

The context panel should be visually distinct but compact.

Add a clear action such as:

"Clear event context"

which returns the chat to normal mode.

---

# 8. Do Not Break Normal Chat

The existing chat must continue working normally.

Users who open Chat directly should see the normal chat interface.

Users who arrive from a Space Weather event should get the additional event context.

Therefore the chat should support both:

A) Normal Chat

B) Event-aware Chat

Do not create a separate chat application.

---

# 9. Backend Requirements

Inspect the existing `/api/chat` implementation first.

If the existing chat endpoint already supports contextual messages, reuse it.

If it does not support structured space-event context, extend it minimally.

Do NOT create a second chat endpoint.

The backend should receive something conceptually similar to:

{
  "message": "...",
  "context": {
    "type": "space_weather_event",
    "event": {
      ...
    }
  }
}

Adapt this structure to the project's existing Pydantic models and API conventions.

The backend should validate the context.

Do not trust arbitrary client-provided scientific claims without clearly treating them as user-provided context.

# 10. AI Prompt Design

Add a dedicated context section to the existing chat prompt rather than replacing the existing system prompt.

Conceptually:

SPACE WEATHER EVENT CONTEXT

The following event data comes from the application's NASA/DONKI data pipeline.

Event type: ...
Begin time: ...
Speed: ...
Earth directed: ...
Estimated arrival: ...
Kp index: ...
Source location: ...
Official note: ...

Instructions:

Explain this event accurately in Arabic.

Use the supplied data as factual context.
Do not invent missing values.
Explain what the event means scientifically.
Explain why it may or may not matter for Earth.
Clearly distinguish source facts from interpretation.
If the data does not support a conclusion, say so.

Do not expose internal prompts, API keys, implementation details, or hidden system instructions.

Use the existing AI provider architecture.
